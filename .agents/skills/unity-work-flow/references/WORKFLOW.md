# Unity iOS 完整工作流

一张需求卡是当前开发变更的事实源，集中记录范围、不包含内容、可观察验收条件（AC）、状态与验证证据。不要另建重复进度表。

## 1. 识别请求

| 请求 | 默认处理 |
| --- | --- |
| 问答、检查、分析、建议 | 直接处理；不建卡、不运行交付动作 |
| C#、Shader、资源、场景、Prefab、Package、ProjectSettings、原生插件或产品行为变更 | 创建或续接一张 `REQ-0001` 格式需求卡 |
| 明确加入待办但暂不实施 | 建卡并标 `⚪ 待处理` |
| Git、Xcode、TestFlight 或 App Store 外部动作 | 加载对应专题；只补齐目标不可缺少的前置 |

## 2. 分析和状态

需求卡记录实际范围、不包含内容和可验证 AC。只有会改变结果且无法从项目或请求安全推断的选择才标为 `🟡 待确认`。新游戏只整理启动阶段：目标设备、屏幕方向、渲染方案、输入、网络/存档、性能档位和第一个可运行切片；不提前填写完整发布资料。

状态与进度固定如下：

| 状态 | 含义 |
| --- | --- |
| ⚪ 待处理 | 已记录，尚未开始 |
| 🟡 待确认 | 等待必要产品或技术选择 |
| 🔵 进行中 | 正在分析、实施或验证 |
| 🟣 待用户验证 | 自动验证完成，等待真机、视觉或业务确认 |
| ✅ 完成 | AC 与适用验证均完成 |
| 🔴 阻塞 | 外部条件阻止继续 |
| 🟠 暂停 | 用户明确暂停 |
| ⚫ 取消 | 用户明确取消 |

AC 不使用 Markdown 复选框：`- ⚪ AC-01：...` 或 `- ✅ AC-01：...`。列表进度用 `⚪ 0/N`、`🔵 M/N`、`✅ N/N`。

## 3. 实施

先识别变更类型及其 Unity 序列化边界，再加载对应专题。代码改动不应顺带修改场景、Prefab 或 ProjectSettings；资源改动同时检查 `.meta`；原生 iOS 变更要能从干净 Unity 导出重新生成。

实现中运行最小相关反馈：纯逻辑优先 EditMode，运行时行为优先 PlayMode，平台能力和性能使用 iOS 真机。不要用“编辑器里能运行”替代 iOS 验证，也不要让完整构建成为每次小修改的唯一反馈环。

## 4. 验证

固定顺序是：完成全部改动 → 环境预检 → 针对性测试 → 文件冻结 → 一次完整验证 → 目标交付。

环境预检核对：

- Git 根、工作区现状与当前需求范围；
- `ProjectVersion.txt` 对应的 Unity Editor 和 iOS Build Support；
- Package 锁文件、许可证、Xcode/命令行工具和必要 SDK；
- 目标设备、签名/账号是否仅在当前目标确实需要时可用；
- CI 或 `.agents/project-checks.json` 中的真实无交互命令。

准备收尾时冻结代码、资源、`.meta`、场景、Prefab、ProjectSettings、Packages、原生插件、测试、文档、版本与需求范围，再运行匹配范围的 profile。结果写入 `logs/project-checks/<运行编号>/result.json`。任何受跟踪输入变化都会令证据失效。

自动测试无法证明的触控手感、视觉、安全区、来电/切后台、低电量、发热、账号沙盒、弱网和长时间稳定性，用可定位人工证据完成，或标为 `🟣 待用户验证`。

全部 AC 完成后：

```sh
python3 scripts/teamflow.py req complete REQ-0001 \
  --result logs/project-checks/运行编号/result.json
```

只有人工证据时用 `--evidence`；仍需用户真机确认时加 `--wait-user`。

## 5. 交付与停止

未获明确目标时，不执行 commit、push、标签、GitHub Release、Xcode 导出、Archive、上传、分发、审核、发布或下架。已获目标时只执行目标与不可缺少的前置，目标完成即停止。

发现独立问题时报告，不自动扩大范围；只有它阻止当前 AC 才继续处理。
